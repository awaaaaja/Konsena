## BUILD — Integrasi seluruh model ke mobile

Pakai folder model yang ada. Baca `model_contract.json`, `preprocessing.json`, `labels.json`, metadata ekspor/seleksi, tokenizer bila relevan, dan `golden_cases.json`. Validasi SHA-256 dan signature graph ONNX aktual. Periksa bukti lisensi distribusi, sumber evaluasi, dan keterbatasan bahasa/domain. Anggap matriks ini baseline dan perbarui dari bukti baru yang bisa direproduksi.

| Model | Folder relatif | Kandidat dan keputusan awal |
|---|---|---|
| Consent NLI | `model/consent_nli/consent_nli/` | FP32 kandidat untuk QA. NLP pasangan teks, max 256, softmax 3 kelas dengan temperature dari kontrak. INT8 gagal validasi. |
| ConsentGap 5 kelas | `model/consentgap/` | FP32 demo sintetis. Parity tercatat 0,60 dengan selisih logit maksimum 0,20694 terhadap batas 0,001. Karantina untuk diagnosis dan perbaikan artefak. Aktifkan sebagai fitur hanya dengan ekspor pengganti yang memenuhi gate. |
| Dark Pattern | `model/dark_pattern/dark_pattern/` | FP32 kandidat untuk QA. RGB NCHW 1×3×224×224, EXIF/resize/normalisasi sesuai kontrak, softmax 2 kelas. INT8 gagal validasi. Fixture tensor yang dirujuk belum ada; pulihkan dari generator asli hanya jika SHA-256 cocok atau minta fixture asli. |
| Privacy Classifier | `model/privacy_classifier/privacy_classifier/` | FP32 eksperimen QA internal, metadata `release_eligible: false`. NLP max 256, sigmoid multi-label 9 kelas dengan threshold per kelas. INT8 gagal validasi. |

1. Siapkan adapter Flutter ke ONNX Runtime Android melalui Kotlin atau runtime kompatibel yang terbukti. Gunakan seam `AnalysisEngine` yang ada. Perluas result types secara kompatibel untuk membedakan hasil nyata, sumber tidak cukup, engine unavailable, dan error. Pertahankan `UnavailableAnalysisEngine` untuk fallback dan riwayat audit yang sudah tersimpan. Pisahkan konfigurasi per model, status kesiapan, opsi debug QA, dan flag release. Default aplikasi tetap aman dengan semua model nonaktif.
2. Gunakan FP32 yang tercatat lolos validasi ekspor untuk menyiapkan jalur debug lokal per model. Urutan yang praktis adalah consent NLI dan Dark Pattern, lalu Privacy Classifier sebagai eksperimen. ConsentGap demo dan semua INT8 yang gagal hanya boleh diuji di harness diagnosis terpisah. Jika komponen terhambat, kerjakan adapter, loading, fallback, atau uji model lain yang bisa diverifikasi. Tandai QA yang berhasil sebagai `QA_ONLY` sampai syarat rilis terpenuhi.
3. Pertahankan model besar di luar aset APK dasar. Sediakan penyiapan paket QA lokal dari katalog dengan verifikasi hash dan ruang penyimpanan. Muat dari penyimpanan privat aplikasi bila diperlukan. Jalankan di luar UI thread dengan satu sesi/inferensi aktif jika itu diperlukan untuk membatasi RAM, lepas tensor dan session, serta tangani file hilang/rusak, ABI unsupported, resource limit, cancellation, dan rollback. Pertahankan alur offline tanpa model. Pemindahan model ke perangkat untuk QA harus memakai perangkat uji dan artefak yang relevan.
4. Jalankan tokenizer WordPiece sesuai tokenizer JSON, termasuk normalisasi, Unicode, urutan pasangan, special token, padding, truncation dan attention mask. Pakai nama, dtype dan shape sesuai graph. Uji tensor preprocessing dan keluaran model secara terpisah. Terapkan kalibrasi per model. Untuk Dark Pattern, input berasal dari screenshot pilihan pengguna dan ROI yang terkait evidence.
5. Pisahkan peran NLI tiga kelas dan ConsentGap lima kelas. Keduanya punya kontrak dan label berbeda. Gunakan NLI hanya untuk pasangan klausa dan pernyataan izin yang memiliki sumber; hasilnya tidak dipetakan ke label lima kelas. Kaitkan tiap hasil ke audit, source ID yang masih aktif, segment/ROI, versi model, dan timestamp. Jika sumber kurang, tampilkan `Bukti belum mencukupi`. UI, histori, dan PDF membedakan anotasi manual, fakta sumber, dan inferensi. Temuan bersifat indikasi untuk ditinjau dan tidak menyatakan pelanggaran UU PDP atau skor risiko rekaan.
6. Jalankan parity dari vektor asli per model pada host dan, bila tersedia, Android. Bandingkan token IDs/mask atau hash/toleransi tensor, finite logits, bentuk, selisih maksimum logit, dan hasil decode. Ambil toleransi dari kontrak/ekspor. Jika paket tidak mencantumkan batas, dokumentasikan batas dari run referensi sebelum menguji Android. Ukur latency, RAM, dan termal di perangkat nyata jika tersedia. Catat `NOT_RUN` untuk perangkat/fixture yang belum tersedia. Untuk rilis, model harus lulus parity Android, penilaian kualitas pada dataset relevan, pengecekan lisensi, pemeriksaan sumber hasil, dan budget perangkat. Bila gagal, nonaktifkan model yang terdampak dan lanjutkan pekerjaan lain.
